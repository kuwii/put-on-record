# Tidy on Record：整理在案

把**已经存在**的工作记录目录整理成"主题子目录 + 索引"的归档结构。本 skill 只整理已有记录文件，不创建新的工作记录，不改写记录中的事实。

记录文件由配套的 `put-on-record`（记录在案）skill 写入，命名规律是 `YYYY-MM-DD-record-{N}-{content}.md`（工作记录）或 `YYYY-MM-DD-task-{N}-{content}.md`（任务记录），`N` 为数字。

## 整理后的形态

```text
<记录根目录>/
├── INDEX.md                    # 总索引（本 skill 维护）
├── <topic-slug>/               # 主题目录：一项工作 / 一个任务
│   ├── INDEX.md                # 主题索引（本 skill 维护）
│   └── {已归档的记录文件}
├── misc/                       # 兜底主题，仅在有归不进去的文件时创建
└── _trash/<YYYYMMDD-HHMMSS>/   # 合并时移出的原件，可恢复
```

- **根层是收件箱**：`put-on-record` 把新记录写在根层；本 skill 每次整理把它们归档进主题目录。整理完成后，根层不应再有符合记录命名规则的文件。
- **只处理符合命名规则的文件**：根层和主题目录中，只认 `YYYY-MM-DD-record-{N}-*.md` / `YYYY-MM-DD-task-{N}-*.md`。其他文件（README、普通笔记、索引等）一律不动。`_trash/` 下的内容不属于记录，不扫描、不索引。
- **不删除任何记录文件**：合并时把原件移入本次的 `_trash/<时间戳>/`，而不是删除。

## 第一步：确定记录根目录与执行模式

1. 用户指定了目录 → 用它。目录不存在 → 报告没有可整理内容（不要创建空目录），结束。
2. 否则，用户级/项目级 AGENTS.md 或项目说明中明确指定了用于写工作记录的目录 → 用它。普通目录（如 `docs/`、`notes/`）不要误认为记录目录。
3. 否则拒绝执行，请用户给出记录根目录。
4. 一次整理一个根目录。用户点名多个目录时逐个独立处理（各自有自己的 `INDEX.md`，互不混杂）。

**执行模式**：

- **交互模式（默认）**：先盘点并给出"整理方案"，等用户确认后再执行；用户调整方案时按调整后的执行。
- **自动模式**：用户明确说"直接整理/不用问/自动执行"，或来自定时任务的指令声明无需确认 → 不询问，按"自动模式约束"一节执行。

## 第二步：盘点现状

1. 扫描记录根目录及主题子目录，找出所有符合命名规则的记录文件；忽略 `_trash/` 下的任何内容。
2. 读根 `INDEX.md`（若存在）与各主题 `INDEX.md`，恢复已有归档状态。
3. **核对索引与文件系统，以文件系统为准修复漂移**：
   - 索引有、文件不存在 → 删掉对应行，并在简报中报告。
   - 主题目录里有记录文件、索引没有 → 读该文件补一行索引。
   - 文件在根层且不在索引中 → 待整理。
   - 主题目录存在但没有 `INDEX.md` → 生成。
   - 根 `INDEX.md` 不存在 → 生成。
4. **防呆**：根层已有 `INDEX.md` 但不是本 skill 生成的（开头部分没有"由 tidy-on-record 维护"标记）→ 停下来问用户怎么处理，绝不覆盖。
5. 没有待整理文件、索引也没有漂移时：不修改任何文件，报告"无需整理"后结束。
6. 待整理的根层记录超过约 50 条时：先只依据文件名和首行标题出一份归类草案；交互模式交用户确认后分批执行，自动模式按草案分批执行并在简报中说明，避免一次读取过多文件。

效率要求：盘点优先用目录列表和索引完成，不要逐篇读正文；只读新的待整理文件、需要生成摘要的文件，以及合并候选。主题判断先看文件名内容词和标题，拿不准再读正文。

## 第三步：归类到主题

- **主题 = 具体的一项工作 / 一个任务**（如"登录鉴权改造"、"wiki 迁移"），不是宽泛领域（如"后端维护"、"杂项"）。判断依据：工作对象、任务名、文件名内容词、标题、正文要点。
- **优先复用已有主题**：读主题 `INDEX.md` 首段的"范围与关键词"判断新记录是否属于该主题。主题数应保持稳定，尽量少新建。
- `task` 记录以**任务**为主题（即使该主题暂时只有 1 条）；对应的 `record` 归入同一任务主题。没有明确任务归属的 `record` 归入其工作内容主题。
- 确实无法归类的记录放入 `misc/`，不要强行创建主题；下次整理可再归类。`misc/` 只在有文件归入时才创建。
- 新建主题时：目录名为英文 kebab-case（几个英文单词 + 连字符，如 `auth-refactor`），稳定、简短、不含日期；在主题 `INDEX.md` 首段写清"范围与关键词"。
- 发现两个已有主题其实是同一项工作 → 合并主题目录（移动文件、合并索引、选更贴切的目录名），并在简报中说明；不要为了美观频繁重命名主题。
- 默认只建一层主题子目录；若某主题记录过多且内容明显发散，在简报中建议拆分，不要自行建第二层。

## 第四步：判定"同类项合并"

**只有同时满足以下条件才合并**：同类型（record 只并 record，task 只并 task）；同一主题；确属同一项工作的连续或重叠部分（同一问题、同一任务的连续推进、同一次改造的不同侧面）；正文要点高度重叠，或本就是同一件事的分次记录。

**不合并**：只是同领域/同仓库但彼此独立的工作；不同项目里的同名问题；工作记录与任务记录；合并后会变成"大杂烩"的组；时间跨度超过约一个月或合并后来源超过 10 条的组（应拆成多个阶段的合并文件）。

拿不准时**不合并**，保持独立文件，并在简报中列为"合并候选"。

**合并文件的写法**：

1. 时间取来源记录的覆盖区间，精确到分钟并带时区，如 `2025-10-28 14:20 ~ 2025-10-30 18:05 (UTC+8)`；各来源的时点可知时，在要点前标注日期，保留可追溯性。
2. 正文按时间顺序或按主题重新组织：合并同类项、去掉重复或啰嗦的表述、统一措辞；**不删除任何事实、结果、时间、远程链接，不添加推测**；保持第一人称视角和自包含规则（不写本地文件路径、"见 xxx"式引用和凭证信息）。
3. 远程资料取并集并去重。
4. 标题概括合并后的整体工作。
5. 文件名用日期区间：`YYYY-MM-DD~YYYY-MM-DD-record-{x}-{content}.md`（任务记录为 `-task-`）。`{x}` 沿用记录命名规则：在该主题目录及其子目录中查找同一区间起始日期、同类型的文件，取最大序号 +1；目录内已有同名文件时继续 +1。
6. 同一主题下若已有与本次合并内容高度相近的合并文件，优先把内容并入它（更新日期区间、相应改名、更新索引），而不是再生成一份新的合并文件。
7. 任务记录合并更保守：只合并对同一任务的重复/补充记录；截止时间等有变化时保留变化事实，不要静默覆盖。

**示例**（两条原始工作记录合并为一条）：

原始记录 A：修复了登录鉴权中间件对 token 过期时间的判断错误；补充了单元测试。
原始记录 B：修复了 token 过期判断的边界问题（时钟偏差场景）；回归测试通过。

合并后：

```markdown
# 修复登录鉴权过期 token 处理

**时间**：2025-10-28 14:20 ~ 2025-10-30 18:05 (UTC+8)

**工作内容**：
- 修复了登录鉴权中间件对 token 过期时间的判断错误，覆盖时钟偏差等边界场景
- 补充了对应的单元测试与回归测试
```

## 第五步：给出整理方案（交互模式必经）

先用一张表向用户展示，等待确认：

| 动作 | 文件 | 去向 / 结果 |
| --- | --- | --- |
| 新建主题 | — | `auth-refactor/`：登录鉴权改造 |
| 归档 | `2025-11-03-record-1-k8s-debug.md` | `k8s-ingress/` |
| 合并 | `2025-10-28-record-1-...`、`2025-10-29-record-1-...` | → `auth-refactor/2025-10-28~2025-10-30-record-1-fix-token.md` |
| 索引 | 根 `INDEX.md`、`auth-refactor/INDEX.md` | 更新 |

同时说明：将移入 `_trash/` 的原件、拿不准而未合并的候选、`misc/` 兜底项。用户确认后执行；用户说暂不整理则结束，不修改任何文件。

## 第六步：执行（顺序固定，可重跑）

1. 新建主题目录。
2. 把根层记录移入主题目录；主题目录内重名时调整 `{x}` 或加区分词，保证文件名唯一。
3. 执行合并：先写好合并文件并自检内容，再把被合并的原件移入 `_trash/<本次时间戳>/<原相对路径>`。
4. 更新受影响主题的 `INDEX.md`（没有变化的不重写）。
5. **最后**更新根 `INDEX.md`。根索引写入视为本次整理完成；中途失败时重新运行即可，以文件系统为准修复。
6. 若记录根目录是 git 仓库：不自动提交，提醒用户用 `git diff` 审查整理结果。

## 索引格式

根 `INDEX.md`：

```markdown
# 工作记录索引

> 由 tidy-on-record 维护，请勿手工编辑 · 最近整理：2025-11-10 21:15 (UTC+8)
> 已归档 42 条（record 30 / task 12），7 个主题；本次整理归档 5 条（合并 2 组），新建主题 1 个。

## 主题

| 主题 | 工作内容 | 记录数 | 最近记录 |
| --- | --- | --- | --- |
| [auth-refactor/](auth-refactor/INDEX.md) | 登录鉴权改造 | 6 | 2025-11-03 |
| [wiki-migration/](wiki-migration/INDEX.md) | wiki 迁移与暗色模式 | 9 | 2025-10-30 |
| [misc/](misc/INDEX.md) | 暂未归类 | 2 | 2025-10-12 |

## 整理备注

- （用户手写的长期规则，整理时必须原样保留）
```

主题 `INDEX.md`：

```markdown
# auth-refactor · 登录鉴权改造

范围与关键词：登录/鉴权改造（token 生命周期、刷新流程、测试）；不混入其他后端维护。
返回 [总索引](../INDEX.md)

| 时间 | 类型 | 文件 | 摘要 |
| --- | --- | --- | --- |
| 2025-10-28 ~ 2025-10-30 | record | [2025-10-28~2025-10-30-record-1-fix-expired-token.md](2025-10-28~2025-10-30-record-1-fix-expired-token.md) | 修复过期 token 判断与刷新后旧 token 问题，补齐测试 |
| 2025-11-03 | task | [2025-11-03-task-1-review-auth-plan.md](2025-11-03-task-1-review-auth-plan.md) | 评审鉴权改造方案 |
```

- 索引表格按时间倒序（最近的在前）；根索引的主题表按"最近记录"倒序。
- 统计口径："条"指已归档记录文件数（合并文件算 1 条，不按来源条数累计）；"本次整理归档 X 条"指本次从根层归档的文件数，合并来源条数只在简报中说明。
- `INDEX.md` 只列已归档文件；根层待整理文件不进索引。
- 主题 `INDEX.md` 的"范围与关键词"是后续整理归类的主要依据，要写具体、可判断。
- 根索引的"整理备注"是用户写的长期规则，重写时必须保留；本 skill 不往里面加内容。
- 索引中的相对路径链接是导航，允许存在；记录文件正文仍不得引用索引或其他本地文件。

## 第七步：自检与简报

自检（发现不通过先修复再结束）：

1. 根层不再有符合命名规则的记录文件（除非用户明确要求保留）。
2. 每个归档文件都出现在所属主题 `INDEX.md` 的表格中，链接指向的文件存在；每个主题目录都有 `INDEX.md`；根索引的主题表与实际目录、记录数一致。
3. 合并文件的时间区间覆盖所有来源、没有新增事实、保持第一人称与自包含（无本地路径、无凭证）。
4. 索引里没有指向不存在文件的链接。
5. `_trash/` 下只有本次整理移出的原件，路径与文件对应。

简报向用户说明：本次归档 N 条、新建主题 M 个、合并 K 组（列出合并前后文件）、跳过/待定 X 条及原因、新建/更新了哪些索引、`_trash` 位置；若记录目录是 git 仓库，提醒用户审查。

## 自动模式约束

无人值守（定时任务）时，只做高置信操作：

- 当天新增的记录只归档、不合并。
- 合并拿不准的一律跳过，写进简报作为候选。
- 不删除文件（只进 `_trash/`）、不清理回收站、不覆盖非本 skill 生成的 `INDEX.md`。
- 遇到无法确定根目录、索引冲突、文件被占用等异常时停止整理，不动文件，把问题写进简报。
- 简报直接输出在回复里（定时任务会回传给用户）。

## 清理回收站

仅当用户明确要求"清理整理回收站/清理 _trash"时执行：先列出 `_trash/` 下各批次的文件与时间，确认后删除 `_trash/` 内的全部内容。平时不自动清理；除 `_trash/` 内容外，本 skill 不删除任何文件。

## 与 put-on-record 的边界

- 本 skill 只整理已有记录文件，不产出新记录；用户要"记录在案"时用 `put-on-record`。
- 记录正文的规则（第一人称、只记事实、自包含、不写本地路径与凭证）沿用 `put-on-record`；合并时不得引入 agent/助手等第三方主体，不得写本地路径。
- 记录目录若已整出主题子目录，`put-on-record` 仍会把新记录写在根层（收件箱）；由本 skill 下次整理归档。

## 定期调用（可选）

本 skill 不创建定时任务、不写脚本。需要定期整理时，在所用 agent 工具里配置周期任务，prompt 形如：`整理在案：整理 <记录根目录>，无人值守，直接执行，不用询问，结束后给出整理简报。` 具体示例见 `references/scheduling.md`（仅在需要配置定时任务时阅读）。

# Put on Record：工作留痕

把当前 session 相关的事情整理成两类 Markdown 文件之一，供日后整理述职报告、在争端中举证、回溯事实、或隔段时间重新理解任务使用：

- **工作记录**（`record`）：记录**用户本人**已完成的工作，全文以用户第一人称"我"叙述（本 session 中你替用户做的事，都算用户做的），**只记已发生的事实，不记计划与推测**。
- **任务记录**（`task`）：记录**用户本人**被布置的工作任务/计划（记录中的"我"是任务承接人）。

两类记录都要求**自包含**：换一台设备、只凭文件本身（加上其中的远程链接）也能读懂，见"自包含：换台设备也能读懂"一节。

一次调用只产出/更新一个文件。

## 第一步：确定记录类型

1. 用户指令中**明确**要求记录工作任务/任务安排/工作计划 → **task**。
2. 否则，session 中存在实质已完成的**工作** → **record**。
3. 否则，session 讨论的中心是用户刚接到、还没开始做的工作任务/计划 → **task**。
4. 否则 → 说明没有明确的记录目标，请用户确认要记录什么。

## 第二步：确定写到哪里

按优先级判断（两类记录相同）：

1. **用户给了 Markdown 文件路径** → 写到那个文件。文件不存在 → 创建（必要时创建父目录）；文件已存在 → 视为**更新记录**，跳到"相似/相同记录合并"一节处理。
2. **用户给了目录** → 在该目录下按"文件命名"一节生成新文件（目录不存在则创建）；写入前先做"相似性检查"。
3. **两者都没给**，但用户或项目级别的上下文（如 AGENTS.md、项目说明文件）中**明确指定**了用于本 skill / 用于写工作记录的目录 → 按第 2 条使用那个目录。普通目录（如 `docs/`、`notes/`）不要误认为记录目录。
4. **否则** → 拒绝执行，请用户给出记录目录或目标文件路径。

## 第三步：相似性检查（仅当要新写文件时）

在目标目录中查找与本次要整理的内容**高度相似**的既有记录，**只查同类型**（task 只和 task 比，record 只和 record 比）：先按文件名中的内容描述词粗筛，再打开疑似候选文件读正文确认——描述词太短，不要只凭文件名判断（例如 `fix-login-bug` 和 `patch-auth-flow` 可能是同一件事）。

- 找到 ≥1 个相似文件 → **停下来询问用户**：列出每个候选（文件路径 + 一句话内容摘要），问是否合并进其中某个既有记录，还是写新文件。
- 用户选择合并进既有文件 → 按"相似/相同记录合并"一节处理；否则写新文件。

## 文件命名

工作记录：

```
YYYY-MM-DD-record-{x}-{work-content}.md
```

任务记录：

```
YYYY-MM-DD-task-{x}-{task-content}.md
```

- `YYYY-MM-DD`：当天日期（四位数年份、两位数月份、两位数日期）。
- `{x}`：序号，**恒有**。两类**各自独立编号**：只在目标目录中查找当天日期、同类型的所有文件（record 查 `YYYY-MM-DD-record-{N}-*.md`，task 查 `YYYY-MM-DD-task-{N}-*.md`，N 为数字），取目前最大序号 +1；当天尚无该类型记录则从 1 开始。
- 内容描述词：高度概括的内容描述，几个英文单词 + 连字符（如 `fix-login-bug`、`investigate-k8s-networking`）。
- 若 session 里明显包含**多个互不相干的工作主题/任务**，先问用户：只记录其中某个，还是笼统合记（合记时与用户确认内容描述词取什么词，可用 `misc` 之类的笼统词）。

## 自包含：换台设备也能读懂

两类记录都可能被长期保存、放进云盘备份、换电脑后继续阅读，因此**不能依赖写记录时那台电脑上的本地文件**——时间一长，原位置的文件变了样，或者换了台电脑，引用就全对不上了。读者只凭这份记录（加上其中的远程链接）就应该能理解内容。

- **不写本地文件路径**：绝对路径（`/Users/…`、`C:\…`）、相对路径（`./docs/x.md`、`../x`、`~/x`）都不写；也不写"见 xxx 文件"、"详见同目录下的 xxx"这类指向本机文件的引用。
- **不引用其他本地记录**：不写"参见 2025-…-record-… 中的…"这种依赖同目录其他记录的表述；需要关联时，把必要信息在本文重述。
- **用名称和描述代替路径**：文件/文档/模块的**名称**（不含路径）、仓库名、系统或服务名可以写；内容用概括、结论或要点内联，让读者不打开原文件也看得懂。记录是纪要，不必精确到每个文件、每行改动——真要抠细节，可以按记录里的仓库名和 commit 去翻 git。
- **远程资源可以写，且优先用固定链接**：内容已上传云盘、或已提交到 git 远端时，写对应链接（云盘文档；git 的 commit / PR / MR / issue）。git 链接优先用 commit、PR 这类固定地址，不记录会随分支移动的链接。
- **严禁**写入密钥、token、密码等凭证信息。

## 工作记录：记录什么

**工作记录是用户本人的工作记录，不是你的工作日志。** 本 session 中你（agent）替用户完成的工作，一律算作用户本人完成的工作来记录：

- **视角**：全文以用户的第一人称"我"叙述（正文语言跟随对话语言，如英文用 "I"）。标题和正文都写成"我做过的事"：可用"我……"句式，也可用省略主语的"……了"句式（如"修复了登录 bug"），但绝不能把用户写成第三方、把你（agent）写成动作主体。
- **归属**：你执行的读取、修改、运行命令、调研、提交等动作，就是用户本人的动作，直接记为用户的工作。不得出现"agent/助手/AI/模型帮用户……""用户要求我……""协助用户……""代用户……""在 agent 协助下……"这类表述，也不得提及记录由 agent 生成或代办。例如：不写"agent 按用户要求修复了登录 bug"，写"我修复了登录 bug"。

**只记录已完成的工作事实**：改了哪些代码、写了什么文档、跑通了什么、调研了什么、提交/汇报/沟通了什么，等等。

- 不记未来计划、未完成部分、未查明的事实、推测；也不写背景/动机/结论。
- 文风：准确、极简、客观，不做任何修饰。
- **写结果，不写文件坐标**：工作内容用读者能直接看懂的结果性描述写清（改了哪个模块的什么行为、产出了什么文档/系统、调研得出了什么），不写"涉及文件/命令"清单，不写本地文件路径（见"自包含"）。
- **远程留痕**：git 已提交的改动记**仓库名 + commit ID**，有远端 commit / PR / MR 链接时一并记；工作成果已上传云盘时记云盘链接。这些远程资料可以单独列一节（见模板）。
- 默认范围是整个 session；**若本 session 之前已成功调用过本 skill**（回看 session 历史找到上次写入的记录文件），则只记录从那次记录之后到当前时刻的工作。若 session 历史中找不到此前的调用记录，则记录整个 session——若有重复，由相似记录合并规则兜底。
- 用户可以用额外说明缩小记录范围，以用户指示为准。

## 任务记录：记录什么

**任务记录是用户本人的任务记录，不是你的任务清单。** 记录中的"我"指用户，任务的主体是用户，不是你（agent）：

- **视角**：以用户视角写任务内容，写成"我接到的、要完成的任务"：可用"我……"句式或省略主语（如"周五前提交迁移方案初稿"）。不得写成"布置给你的任务"、把你（agent）写成任务承接人，也不得出现"用户要求我……""用户让我……"这类把用户写成第三方的表述。
- **布置人/来源**：指把任务布置给用户（"我"）的人或渠道（如某领导、某会议、某工单）；用户自己发起的任务写"本人"或省略。
- **只记录任务本身**：任务内容、背景、完成标准、截止时间、布置人/来源等。不记打算怎么做、进度推测、个人意见；任务若实际由用户委托给你（agent）执行，也只记任务本身，不写"交给 agent 做""完成后发给用户"这类协作细节。
- 文风：与工作记录一致——准确、极简、客观，不做任何修饰。
- **自包含**（见"自包含：换台设备也能读懂"）：读者只凭这个文件（加上其中的远程链接）就能完整理解任务。
  - 涉及本地文件/文档时，把相关内容**内联**（摘录要点并写明来源文件名称，不写路径），不允许写"见 ./xxx"；无法内联的细节宁可概括，也不要让读者去翻本机文件。
  - 任务的相关资料已上传云盘、或 git 远端可访问时，记对应链接。
- **写之前先审视当前上下文**：检查用户级与项目级 AGENTS.md、已配置的 skill 及其描述、可用的 MCP 工具、当前项目的 README/文档，凡与任务相关的内容（项目定位、约定规范、工单信息等）都用来补全背景，且**把相关事实内联**进文件，不写"AGENTS.md 说"、"参考某某 skill"之类的出处说明。任务细节与 MCP 工具相关时（如日历、工单系统），可以**调用其只读能力**获取信息（如确认截止时间、读工单内容），但不得执行任何写操作。
- 无法确定的字段（完成标准、截止时间、布置人等）：可知才写，不可知省略，不编造。

## 记录模板（极轻，允许自由发挥）

工作记录：

```markdown
# {工作一句话标题，如"修复登录鉴权 bug"}

**时间**：{时间}

**工作内容**：
- {我做的事 1，如"修复了登录鉴权中间件对过期 token 的判断错误"}
- {我做的事 2}

**远程资料**（可选，没有就省略整节）：
- {工作成果对应的远程链接，如云盘文档、git 远端 commit / PR / MR；或"{仓库名} commit {commit ID}"}
```

任务记录：

```markdown
# {任务一句话标题，如"编写 wiki 迁移方案初稿"}

**布置时间**：{时间}

**布置人/来源**：{把任务布置给我的人/渠道，若可知}

**任务内容**：
- {我接到的任务，自包含描述}

**完成标准/截止时间**：{若可知}

**相关背景**：{理解任务所需的背景}
```

- **时间**：若 session 上下文中已有相关时间区间或重要时刻（工作记录如某改动提交于何时、某问题反馈于何时；任务记录如任务布置于何时），记录下来（区间或若干时刻均可）；否则记录本次写记录的时刻。精确到分钟并带时区，如 `14:30 ~ 15:42 (UTC+8)` 或 `2025-11-03 15:42 (UTC+8)`。
- 工作记录的标题与"工作内容"一律以用户第一人称叙述（"我……"或省略主语），**不得出现 agent、助手、AI 等第三方主体**：agent 做的事算用户做的。
- 任务记录的"任务内容"一律以用户视角写（"我接到的任务"或省略主语），**不得把 agent 写成任务承接人**；"布置人/来源"是把任务布置给用户（"我"）的人或渠道。
- 工作记录**不写本地文件路径与命令清单**（见"自包含"）：工作内容用结果性描述；git 已提交的改动在"远程资料"里记仓库名 + commit ID，有远端链接更好；云盘等远程资源记链接。
- 记录正文语言跟随对话语言。
- 模板覆盖不到的场景（如争端场景需要详细陈述事件经过与时间点）按需调整；用户的额外说明优先。

## 相似/相同记录合并

两类记录均适用：用户直接指定了一个已存在的文件，或相似性检查后用户确认合并进某个既有文件。

1. 将本次工作/任务内容并入该既有记录。
2. 将全文改写成一次成文的风格——成品看不出任何被更新过的痕迹。
3. **时间部分保持不变**。
4. 重新审查文件名中内容描述词部分是否仍能代表更新后的整体内容：不能则更新文件名（相应重命名文件）。文件名本就不符合上述命名规范的，不强行重命名。

## 完成后

1. **自检**：通读记录，确认没有本地文件路径（`/`、`./`、`~/`、`C:\` 等）、"见 xxx"式引用、其他本地记录引用和凭证信息；有则改写成结果性描述或删除。
2. 向用户简报：记录已写入（新建还是更新）、类型及文件路径。无需赘述。
